# API Contract — Harmonized Burning Activity Calendar

NASA Space Apps Challenge 2026 · Harmonization of MODIS and VIIRS Hot Spots · Region: Australia
Backend architecture: `BACKEND_ARCHITECTURE_v2` · Contract version: **1.1**

This document is for the frontend team. It defines every endpoint, what to send, and exactly what comes back, so the frontend can be built and mocked before the backend is finished. If the backend needs to change anything here, the contract version goes up and the change is listed in §15.

---

## 1. Basics

| Item | Value |
|---|---|
| Base URL (local) | `http://localhost:8000` |
| Base URL (production) | **Public HTTPS URL, to be confirmed** (e.g. Render, Railway, Fly.io or a Cloudflare Tunnel). The frontend is served over HTTPS from GitHub Pages, and browsers block calls from an HTTPS page to a plain `http://` API. |
| Prefix | every endpoint starts with `/api` |
| Method | `GET` only |
| Format | JSON (`application/json`), except `/api/hotspots.csv` |
| Auth | none. The FIRMS key stays on the server; the frontend never sees it. |
| CORS | Must allow `http://localhost:5173` (dev) and `https://its-thakshila.github.io` (production, GitHub Pages) |
| Interactive docs | `http://localhost:8000/docs` (generated by FastAPI) |

### 1.1 Dates are local fire-days

All `start` / `end` parameters and every `fire_date` in responses are **local fire-days** (`YYYY-MM-DD`), not UTC dates.

- A fire-day runs from 6 am to 6 am local solar time, so a night pass at 1:30 am belongs to the previous evening's fire-day.
- This is the same day definition the harmonization model uses, so the calendar, the daily chart and the CSV download always agree.
- Row responses also include the raw UTC `acq_date` and `acq_time` from the satellite record.

### 1.2 Counts are weighted floats

`count` values are **floats**, not integers. Rows generated by the model (2000–2011 and outage days) carry a `weight` slightly above 1, which corrects for small fires the model cannot place. **Round counts for display** (`Math.round`). Never count rows yourself to get a total; sum `weight` instead.

### 1.3 Missing data is not zero fires

A day with no data is returned with `has_data: "none"` and `count: null`. **Never draw `null` as 0.** Show it as "no data" (for example hatched or grey) in the calendar and charts.

## 2. Common query parameters

| Parameter | Type | Required | Example | Rules |
|---|---|---|---|---|
| `lat1` | number | yes | `-30` | −90 … 90 |
| `lon1` | number | yes | `148` | −180 … 180 |
| `lat2` | number | yes | `-37` | −90 … 90 |
| `lon2` | number | yes | `153` | −180 … 180 |
| `start` | `YYYY-MM-DD` | yes* | `2019-11-01` | ≥ `2000-11-01` |
| `end` | `YYYY-MM-DD` | no | `2019-11-30` | ≥ `start`, ≤ today. Omit for a single day (`end = start`). |
| `types` | comma list of int | no | `0` or `0,2` | `0` vegetation fire (default) · `2` static / industrial · `3` offshore |

\* `/api/calendar` and `/api/anomaly` use their own date parameters (see their sections).

**Box rules**

- `(lat1, lon1)` and `(lat2, lon2)` are any two opposite corners of the drawn rectangle, in any order. The backend sorts them.
- The box must lie **fully inside the Australia box**: longitude 112 … 154, latitude −44 … −9. Otherwise the request fails with `BOX_OUTSIDE_COVERAGE`.
- The response always echoes the normalised box as `query.bbox`.

Example: `/api/daily?lat1=-30&lon1=148&lat2=-37&lon2=153&start=2019-11-01&end=2019-11-30`

## 3. Response envelope

Every JSON response (except `/api/health`) has this shape:

```json
{
  "query": {
    "bbox": {"min_lat": -37, "max_lat": -30, "min_lon": 148, "max_lon": 153},
    "start": "2019-11-01",
    "end": "2019-11-30",
    "types": [0]
  },
  "partial": false,
  "missing_dates": [],
  "warnings": [],
  "generated_at": "2026-11-14T08:30:12Z",
  "data": { }
}
```

| Field | Meaning |
|---|---|
| `query` | The request as the backend understood it (normalised box, resolved dates). |
| `partial` | `true` if any day in the range is missing or incomplete. The response is still usable. |
| `missing_dates` | Fire-days in the range with `has_data` = `"none"` or `"partial"`. |
| `warnings` | List of `{code, message}` objects to show as notices (§10). |
| `generated_at` | UTC timestamp of the response. |
| `data` | Endpoint-specific payload. |

## 4. `GET /api/daily` — one value per fire-day

**Use for:** the daily time-series chart and the day-level calendar view.

**Parameters:** common (§2). Maximum range: the whole record (2000-11-01 → today).

**`data`**

```json
{
  "days": [
    {
      "fire_date": "2005-11-01",
      "count": 612.4,
      "count_day": 401.8,
      "count_night": 210.6,
      "frp_sum": 7120.5,
      "n_rows": 571,
      "origin_mix": {"ml": 1.0},
      "has_data": "full",
      "uncertainty": 0.11,
      "daynight_reliable": true
    },
    {
      "fire_date": "2001-06-20",
      "count": null,
      "count_day": null,
      "count_night": null,
      "frp_sum": null,
      "n_rows": 0,
      "origin_mix": {},
      "has_data": "none",
      "uncertainty": null,
      "daynight_reliable": true
    }
  ],
  "totals": {
    "count": 18452.7,
    "frp_sum": 215034.1,
    "days_with_data": 29,
    "days_total": 30
  }
}
```

| Field | Type | Meaning |
|---|---|---|
| `fire_date` | string | Local fire-day. **Every day in the range appears exactly once, in order**, including days with no data. |
| `count` | float \| null | Weighted hotspot detections (VIIRS-equivalent). `null` when `has_data` is `"none"`. |
| `count_day` / `count_night` | float \| null | Split by day pass (~1:30 pm) and night pass (~1:30 am). |
| `frp_sum` | float \| null | Total fire radiative power, MW (weighted). |
| `n_rows` | int | Raw number of rows (unweighted). For debugging only. |
| `origin_mix` | object | Share of `count` by source; values sum to 1. Keys: `real`, `ml`, `gapfill`, `firms_nrt`, `firms_sp`. |
| `has_data` | `"full"` \| `"partial"` \| `"none"` | `full` = complete data · `partial` = incomplete satellite delivery or next to an outage · `none` = no data at all (draw as "no data", never as 0). |
| `uncertainty` | float \| null | Typical relative daily error: `0` for real data, `0.11` = ±11%. Use for error bands. |
| `daynight_reliable` | bool | `false` on gap-filled days in 2022–2025: show only the total, not the day/night split. |

**`origin` values**

| Value | Meaning | Periods |
|---|---|---|
| `real` | Real VIIRS S-NPP observation | 2012-01-20 → 2025-12-31 |
| `ml` | Model-generated from MODIS | 2000-11-01 → 2011-12-31 |
| `gapfill` | Model-generated on VIIRS outage days | ~60 days in 2012–2025 |
| `firms_nrt` | Real VIIRS from FIRMS, near-real-time (may still change for ~3 days) | 2026 → today |
| `firms_sp` | Real VIIRS from FIRMS, final archive | 2026, once available |

**`uncertainty` by period**

| Period / origin | Value |
|---|---|
| `real`, `firms_nrt`, `firms_sp` | `0` |
| `ml`, Jul 2002 – 2011 | `0.11` |
| `ml`, Nov 2000 – Jun 2002 (Terra-only) | `0.16` |
| `gapfill`, 2012 | `0.11` |
| `gapfill`, 2022–2025 | `0.13` |

For a day mixing origins, `uncertainty` is the count-weighted average.

## 5. `GET /api/calendar` — year × month heatmap

**Use for:** the main burning activity calendar (rows = years, columns = months) and the monthly seasonal profile.

**Parameters**

| Parameter | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `lat1`, `lon1`, `lat2`, `lon2` | number | yes | — | As §2 |
| `start_year` | int | no | `2000` | First year shown |
| `end_year` | int | no | current year | Last year shown |
| `types` | comma list | no | `0` | As §2 |

**`data`**

```json
{
  "cells": [
    {"year": 2000, "month": 11, "count": 41230.5, "has_data": "full",
     "days_with_data": 30, "days_total": 30, "complete": true,
     "main_origin": "ml", "uncertainty": 0.16},
    {"year": 2019, "month": 12, "count": 512880.2, "has_data": "full",
     "days_with_data": 31, "days_total": 31, "complete": true,
     "main_origin": "real", "uncertainty": 0},
    {"year": 2026, "month": 11, "count": 20311.0, "has_data": "partial",
     "days_with_data": 14, "days_total": 30, "complete": false,
     "main_origin": "firms_nrt", "uncertainty": 0}
  ],
  "climatology": [
    {"month": 1, "median": 30120.4, "p10": 14210.9, "p25": 21003.2, "p75": 44010.7,
     "p90": 70544.3, "min": 9122.0, "max": 120334.9, "years_used": 25}
  ],
  "scale": {"min": 0, "max": 512880.2, "p95": 220400.0}
}
```

| Field | Meaning |
|---|---|
| `cells` | One entry per year × month in the range. Months before 2000-11 or after the current month are **not included**. |
| `cells[].count` | Weighted total for the month. `null` if no day in the month has data. |
| `cells[].has_data` | `"full"` all days have data · `"partial"` some days missing · `"none"` no day has data |
| `cells[].complete` | `false` for the current month (still in progress). Don't compare it directly with full months; use `/api/anomaly`, which handles month-to-date. |
| `cells[].main_origin` | Origin with the largest share. Use it to mark modelled years (for example a dotted border for `ml`). |
| `climatology` | 12 entries (month 1–12): median and spread (p10, p25, p75, p90, min, max) of that month across all **complete** years in the range. Use for the seasonal profile, the "typical month" line, and to colour every calendar cell with the same five categories as `/api/anomaly` (below p10 = well below … above p90 = well above). |
| `scale` | Suggested colour-ramp limits. `p95` is a good ramp maximum so one extreme month (e.g. Black Summer, Dec 2019) doesn't wash out every other cell. |

## 6. `GET /api/anomaly` — how does a month compare?

**Use for:** "this month vs the historical median" panel, and the year-by-year bar chart for one month.

**Parameters**

| Parameter | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `lat1`, `lon1`, `lat2`, `lon2` | number | yes | — | As §2 |
| `month` | `YYYY-MM` | yes | — | The month to assess |
| `baseline_start_year` | int | no | `2001` | First year of the baseline |
| `baseline_end_year` | int | no | year before `month` | Last year of the baseline |
| `types` | comma list | no | `0` | As §2 |

**Month in progress:** if `month` is the current month, the backend compares **month-to-date**: for example 1–14 November 2026 against 1–14 November of every baseline year. `data.compared_days` says which days were used.

**`data`**

```json
{
  "month": "2026-11",
  "compared_days": {"from_day": 1, "to_day": 14, "month_to_date": true},
  "value": 20311.0,
  "baseline": {
    "years": [2001, 2025],
    "n_years": 25,
    "median": 15840.2,
    "mean": 18922.7,
    "std": 9010.3,
    "p10": 7400.1, "p25": 11002.6, "p75": 23120.9, "p90": 31544.0
  },
  "percent_of_median": 128.2,
  "z_score": 0.15,
  "rank": 7,
  "rank_of": 26,
  "category": "above",
  "has_data": "full",
  "history": [
    {"year": 2001, "value": 9120.4, "has_data": "full", "main_origin": "ml"},
    {"year": 2019, "value": 61022.8, "has_data": "full", "main_origin": "real"}
  ]
}
```

| Field | Meaning |
|---|---|
| `value` | Weighted count for the month (or month-to-date). |
| `baseline` | Statistics over the baseline years, same days of the month. Years with missing days are left out; `n_years` says how many were used. |
| `percent_of_median` | `100 × value / median`. 128.2 = 28% above typical. |
| `z_score` | `(value − mean) / std`. |
| `rank` / `rank_of` | Position among all years including this one, **1 = highest activity**. |
| `category` | Ready-made label for colouring: `well_below` (< p10) · `below` (p10–p25) · `normal` (p25–p75) · `above` (p75–p90) · `well_above` (> p90). |
| `history` | The same month in every baseline year plus the assessed year, for a bar chart. |

## 7. `GET /api/grid` — map density (0.1° cells)

**Use for:** the map. It shows a whole month (or any range up to `limits.grid_max_days`) for any box, including all of Australia, which the row endpoints refuse as too large. Model rows are only statistically placed, so they should be shown aggregated to 0.1° cells anyway.

**Parameters:** common (§2). Maximum range: `limits.grid_max_days` days (§12).

**`data`**

```json
{
  "res": 0.1,
  "total": 512880.2,
  "max_count": 1840.6,
  "cells": [
    {"lat": -37.6, "lon": 149.1, "count": 1840.6, "frp_sum": 95210.4, "main_origin": "real"},
    {"lat": -37.5, "lon": 149.1, "count": 1210.0, "frp_sum": 60033.0, "main_origin": "real"}
  ]
}
```

| Field | Meaning |
|---|---|
| `res` | Cell size in degrees (always `0.1`). |
| `cells[].lat`, `cells[].lon` | **South-west corner** of the cell. The cell covers `lat … lat + 0.1` and `lon … lon + 0.1`. |
| `cells[].count` | Weighted detections in the cell over the range (same weighting as §1.2). |
| `cells[].frp_sum` | Total FRP in the cell (MW, weighted). |
| `cells[].main_origin` | Origin with the largest share in the cell (see §4). |
| `total` | Sum of `count` over all cells. Equals `/api/daily` `totals.count` for the same query. |
| `max_count` | Largest cell `count`, for the colour ramp. |

Only cells with `count > 0` are returned. Days without data are listed in the envelope's `missing_dates`, as for the other endpoints. Errors: `QUERY_TOO_LARGE` if the range is longer than `limits.grid_max_days`.

## 8. `GET /api/hotspots` — individual detections (JSON)

**Use for:** drawing hotspot points on the map.

**Parameters:** common (§2), plus:

| Parameter | Type | Default | Max | Meaning |
|---|---|---|---|---|
| `limit` | int | `5000` | `20000` | Rows per page |
| `offset` | int | `0` | — | Rows to skip |

**Size limit.** Row endpoints refuse very large requests with `QUERY_TOO_LARGE`. Request size = **box area in square degrees × number of days**. The limits are published in `/api/meta` (`limits.hotspots_max_deg2_days`, `limits.csv_max_deg2_days`) so the frontend can warn before sending. For a large box or a long range, show `/api/daily` or `/api/calendar` instead, or draw a density layer. Rough guide: a whole-Australia box works for a few days; a 2° × 2° box works for about a year.

**`data`**

```json
{
  "total": 1834,
  "limit": 5000,
  "offset": 0,
  "next_offset": null,
  "rows": [
    {
      "latitude": -38.27324,
      "longitude": 146.38933,
      "bright_ti4": 348.58,
      "scan": 0.39,
      "track": 0.37,
      "acq_date": "2019-01-01",
      "acq_time": "0401",
      "satellite": "N",
      "instrument": "VIIRS",
      "confidence": "n",
      "version": "2",
      "bright_ti5": 310.69,
      "frp": 7.71,
      "daynight": "D",
      "type": 0,
      "fire_date": "2019-01-01",
      "pass": "D",
      "origin": "real",
      "weight": 1.0
    }
  ]
}
```

| Field | Type | Meaning |
|---|---|---|
| `latitude`, `longitude` | float | Pixel centre (WGS84). |
| `bright_ti4` | float | Fire-channel brightness temperature (K). |
| `scan`, `track` | float | Pixel size (km), ~0.375. |
| `acq_date` | string | **UTC** date of the satellite pass. |
| `acq_time` | string | **UTC** time, `HHMM`, always 4 characters (`"0401"`). Keep as string. |
| `satellite`, `instrument` | string | Always `"N"`, `"VIIRS"`. |
| `confidence` | `"l"` \| `"n"` \| `"h"` | Low / nominal / high. |
| `version` | string | `"2"` real, `"ML-XGB-1.0"` model, `"ML-XGB-1.0-gapfill"` gap-fill. Use `origin` instead in the UI. |
| `bright_ti5` | float | Background-channel brightness temperature (K). |
| `frp` | float | Fire radiative power (MW). |
| `daynight` | `"D"` \| `"N"` | Day or night pass. |
| `type` | int | `0` vegetation · `2` static / industrial · `3` offshore. |
| `fire_date` | string | Local fire-day (§1.1). |
| `pass` | `"D"` \| `"N"` | Pass, from local solar time. Equal to `daynight` in ~99% of rows. |
| `origin` | string | See the table in §4. |
| `weight` | float | `1.0` for real and FIRMS rows; 1.04–1.64 for model rows. |

**Model rows on the map.** Rows with `origin` = `ml` or `gapfill` have statistically sampled positions (accurate to a few km, not to the pixel). Show them with a different style, for example hollow markers, and say so in the legend. On zoomed-in views they should not be presented as exact fire locations.

Rows are sorted by `acq_date`, `acq_time`.

## 9. `GET /api/hotspots.csv` — CSV download

**Use for:** the "Download CSV" button. Link to it directly (`<a href="…" download>`); the browser saves the file.

**Parameters:** common (§2). No pagination: the whole result is streamed. The same `QUERY_TOO_LARGE` rule applies, with the higher ceiling `limits.csv_max_deg2_days` from `/api/meta`.

**Response**

- `Content-Type: text/csv`
- `Content-Disposition: attachment; filename="hotspots_<min_lat>_<min_lon>_<max_lat>_<max_lon>_<start>_<end>.csv"`
- Columns, in this order: the 15 FIRMS VIIRS columns, then `fire_date`, `origin`, `weight`:

```
latitude,longitude,bright_ti4,scan,track,acq_date,acq_time,satellite,instrument,confidence,version,bright_ti5,frp,daynight,type,fire_date,origin,weight
-38.27324,146.38933,348.58,0.39,0.37,2019-01-01,0401,N,VIIRS,n,2,310.69,7.71,D,0,2019-01-01,real,1.0
```

Errors on this endpoint come back as JSON (§11) with a non-200 status, so check `response.ok` if you fetch it instead of linking.

## 10. Warnings

`warnings` is a list of `{"code": string, "message": string}`. Show `message` as a notice; use `code` for logic.

| Code | When | Suggested UI |
|---|---|---|
| `SMALL_BOX_MODEL_PERIOD` | Box smaller than 0.5° × 0.5° and the range includes 2000–2011 or gap-fill days | Note: "Model-based years are reliable only as totals for small areas" |
| `MODEL_DATA_INCLUDED` | Range includes `ml` or `gapfill` data | Legend entry / info icon |
| `FIRMS_UNAVAILABLE` | FIRMS could not be reached; some 2026 days are missing | Banner: recent data temporarily unavailable |
| `FIRMS_LOW_DELIVERY` | A 2026 day has suspiciously few detections (likely satellite outage) | Mark day as partial |
| `RECENT_DATA_PROVISIONAL` | Range includes the last 3 days (NRT data still changing) | Small note on recent days |
| `KNOWN_OUTAGE` | Range includes a day where no satellite data exists | Mark days as "no data" |
| `DAYNIGHT_UNRELIABLE` | Range includes 2022–2025 gap-fill days | Hide day/night split on those days |
| `MONTH_IN_PROGRESS` | `/api/anomaly` on the current month | Show "month to date" label |

## 11. Errors

Errors use HTTP status codes with this body:

```json
{
  "error": {
    "code": "BOX_OUTSIDE_COVERAGE",
    "message": "The selected area must be inside Australia (lon 112 to 154, lat -44 to -9).",
    "field": "lon2",
    "hint": null
  }
}
```

| Status | `code` | Cause |
|---|---|---|
| 400 | `MISSING_PARAMETER` | A required parameter is missing (`field` names it) |
| 400 | `INVALID_PARAMETER` | Wrong format, e.g. `start=2019/11/01` |
| 400 | `COORDINATE_OUT_OF_RANGE` | Latitude/longitude outside valid ranges |
| 400 | `BOX_OUTSIDE_COVERAGE` | Box not fully inside the Australia box |
| 400 | `EMPTY_BOX` | Both corners give a zero-width or zero-height box |
| 400 | `INVALID_DATE_RANGE` | `start` after `end`, `start` before 2000-11-01, or `end` after today |
| 400 | `QUERY_TOO_LARGE` | Row endpoint request too big; `hint` suggests `/api/daily` or a smaller box/range |
| 502 | `UPSTREAM_ERROR` | Only if the request needs **only** 2026 data and FIRMS fails with nothing cached. Otherwise a FIRMS failure gives `partial: true` instead of an error. |
| 500 | `INTERNAL_ERROR` | Bug. Show a generic error. |

| `grid_max_days` | Longest range (days) that `/api/grid` accepts. |

## 13. TypeScript types

```ts
export type HasData = "full" | "partial" | "none";
export type Origin = "real" | "ml" | "gapfill" | "firms_nrt" | "firms_sp";
export type Category = "well_below" | "below" | "normal" | "above" | "well_above";

export interface BBox { min_lat: number; max_lat: number; min_lon: number; max_lon: number }
export interface Warning { code: string; message: string }

export interface Envelope<T> {
  query: { bbox: BBox; start?: string; end?: string; types: number[]; [k: string]: unknown };
  partial: boolean;
  missing_dates: string[];
  warnings: Warning[];
  generated_at: string;
  data: T;
}

export interface DailyValue {
  fire_date: string;
  count: number | null;
  count_day: number | null;
```

## 14. Frontend notes

1. **Response times.** Local data (2000–2025) answers in under a second. A request touching 2026 days that aren't cached yet triggers a FIRMS fetch and can take **5–20 seconds** the first time. Show a loading state, and use a client timeout of at least 60 s. The team will pre-load 2026 before the demo, so it should be fast then.
2. **Debounce.** Don't send a request on every mouse move while drawing the box: wait until the rectangle is finished, or debounce by ~400 ms.
3. **Cache on the client.** Responses for past dates never change. It's safe to cache them in memory keyed by the full URL. Only ranges including the last 3 days may change.
4. **Calendar colour ramp.** Use a sequential ramp from `0` to `scale.p95`, clamping values above. Use a distinct style for `has_data: "none"` (no data) and `"partial"`, and mark `main_origin: "ml"` cells (modelled years).
5. **Anomaly colours.** Use a diverging ramp keyed on `category` or `percent_of_median`, centred on `normal` / 100%.
6. **Request order for a new box:** `/api/calendar` (main view) → `/api/anomaly` for the latest month → `/api/grid` for the map → `/api/daily` when a month is clicked → `/api/hotspots` only when the map is zoomed into a small area or short range.
